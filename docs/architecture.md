# Архитектура CodeSplit

## Назначение

CodeSplit должен безопасно разделять крупные файлы C и C++ на меньшие файлы, сохраняя
компилируемость и поведение программы. Безопасность преобразования важнее возможности обработать
любой входной файл автоматически.

## Текущая архитектура

```mermaid
flowchart TD
    CLI["CLI: параметры и команды"]
    Source["Физический анализ: размер и строки"]
    Port["Порты: compilation command и callable inventory"]
    Clang["Адаптер: Clang LibTooling"]
    Fallback["Адаптер: LibTooling недоступен"]
    Database["compile_commands.json"]
    Reports["Текстовый и JSON-отчёты"]

    CLI --> Source
    CLI --> Port
    Database --> Clang
    Clang --> Port
    Fallback --> Port
    Source --> Reports
    Port --> Reports
```

`codesplit_core` не зависит от типов LLVM и Clang. `codesplit_clang` предоставляет одну из двух
реализаций общего интерфейса: настоящую загрузку compilation database или явный результат о
недоступности LibTooling.

## Границы зависимостей

```mermaid
flowchart LR
    LLVM["LLVM: базовая инфраструктура"]
    Clang["Clang: frontend C/C++"]
    Tooling["LibTooling: API для инструментов"]
    Adapter["codesplit_clang"]
    Core["codesplit_core"]
    App["codesplit"]

    LLVM --> Clang
    Clang --> Tooling
    Tooling --> Adapter
    Core --> App
    Adapter --> App
```

Публичные модели CodeSplit используют только стандартные C++-типы. Объекты `clang::ASTContext`,
`clang::Decl`, `clang::SourceManager` и другие типы frontend не должны выходить за границу
`src/clang`.

Текущая AST-инвентаризация возвращает собственные структуры `CallableDefinition` и
`CallableConstraint`. Она находит определения свободных функций и out-of-line методов в основном
файле, вычисляет строки, байтовые смещения и размер исходного диапазона. Макросы и слишком большие
сущности не отбрасываются молча: они остаются в отчёте вместе с причинами, ограничивающими
преобразование. Каноническая декларация Clang связывает out-of-line метод с точным объявлением и
классом-владельцем, включая перегруженные методы. Наружу эта связь выходит как собственные
`SourceRange` и строковый `symbol_id`, сформированный из USR; указатели AST не покидают адаптер.
Диагностики Clang преобразуются в `FrontendDiagnostic` непосредственно во время frontend-анализа,
пока доступен `SourceManager`. Предупреждения сохраняются вместе с inventory, а ошибки делают
результат неуспешным и исключают использование частично построенного списка сущностей.

Первый срез графа зависимостей представлен структурой `CallableDependency`. Для каждого тела
адаптер обходит `CallExpr`, принимает только вызовы с однозначным `getDirectCallee()` и связывает
USR вызывающей сущности с USR канонической декларации цели. Повторные вызовы одной цели внутри
одного тела сворачиваются в одно ребро. Косвенные вызовы через указатели, функции высшего порядка и
возможные цели виртуальной диспетчеризации не угадываются: отсутствие доказанной цели безопаснее
ложной зависимости.

Зависимости `type_reference` строятся по явным `TagTypeLoc` внутри декларации и тела callable.
Таким образом учитываются `struct`, `class`, `union` и `enum` в сигнатурах и локальных объявлениях,
а встроенные типы не создают рёбер. Повторные упоминания одной канонической декларации типа
дедуплицируются по паре USR источника и цели отдельно от других видов зависимости.

Прямые обращения `DeclRefExpr` к `VarDecl` с глобальным временем хранения представлены рёбрами
`global_read` и `global_write`. Левая часть простого присваивания создаёт запись, compound
assignment и `++/--` — чтение и запись, остальные прямые обращения — чтение. Статические локальные
переменные исключены из этого среза. Классификация проходит через прозрачные скобки и не зависит от
их наличия в исходном тексте.

Прямые include-зависимости собираются на уровне препроцессора, потому что после построения AST
директивы `#include` уже не представлены обычными узлами дерева. `PPCallbacks` сохраняет только
директивы из основного файла: написанное имя, форму с кавычками или угловыми скобками, разрешённый
путь и точный исходный диапазон директивы. Подключения внутри заголовков не смешиваются с прямыми
рёбрами основной единицы трансляции.

Публичный результат сохраняет исходную команду компиляции. Перед внутренним запуском `ClangTool`
адаптер удаляет из её копии только compile-only аргументы `-c` и `/c`: syntax-only action не создаёт
объектный файл, а сохранение этих флагов порождало служебную диагностику, не относящуюся к проекту.
Стандарт языка, определения, include-каталоги и остальные семантические параметры не изменяются.

## Уровни декомпозиции

### Перенос целых семантических единиц

Первый уровень сохраняет внутреннее устройство переносимого кода:

- перенос определения свободной функции в другой `.c` или `.cpp`;
- перенос объявления класса в отдельный `.h` или `.hpp`;
- перенос out-of-line реализаций методов класса в отдельный `.cpp`;
- перенос связанных include и forward declaration;
- обновление мест подключения нового заголовка.

Такое преобразование работает с границами деклараций AST. Оно остаётся нетривиальным из-за
шаблонов, inline-методов, макросов, include-циклов и требований к полноте типов, но не меняет тело
функции.

### Декомпозиция большой функции или метода

Если одна функция или один метод превышает целевой размер файла, перенос целой функции не решает
задачу. Необходимо выделить часть тела в новую функцию или метод.

```mermaid
flowchart LR
    Body["Тело функции больше лимита"]
    Regions["Кандидатные области AST/CFG"]
    Inputs["Входные зависимости"]
    Outputs["Изменяемые и live-out значения"]
    Control["return, break, continue, goto, exceptions"]
    Plan["План извлечения функции"]
    Verify["Повторный анализ и сборка"]

    Body --> Regions
    Regions --> Inputs
    Regions --> Outputs
    Regions --> Control
    Inputs --> Plan
    Outputs --> Plan
    Control --> Plan
    Plan --> Verify
```

Этот уровень требует не только AST, но и анализа потока управления и данных. Автоматическое
извлечение запрещается, если CodeSplit не может доказать сохранение области видимости, времени
жизни объектов и управляющего поведения.

## Инварианты безопасности

1. Анализ использует настоящую команду компиляции или явно предоставленные пользователем флаги.
2. Ошибки frontend не скрываются и блокируют изменяющие операции.
3. Код из macro expansion не переносится как обычный текст.
4. Сначала строится и проверяется план изменений, затем выполняется запись.
5. Набор изменений применяется атомарно либо не применяется вовсе.
6. После преобразования повторяются синтаксический анализ, сборка и тесты проекта, если они
   доступны.
7. При неоднозначности инструмент формирует диагностический результат вместо предположения.

## Разрешение конфликтов

```mermaid
flowchart LR
    Facts["Факты AST, CFG и source ranges"]
    Constraints["Набор структурированных ограничений"]
    Strategies["Кандидатные стратегии разрешения"]
    Decision{"Доказана единственная безопасная стратегия?"}
    Auto["Разрешить автоматически"]
    Confirm["Показать варианты пользователю"]
    Block["Заблокировать преобразование"]
    Verify["Повторный анализ, сборка и тесты"]

    Facts --> Constraints
    Constraints --> Strategies
    Strategies --> Decision
    Decision -->|да| Auto
    Decision -->|несколько вариантов| Confirm
    Decision -->|нет| Block
    Auto --> Verify
    Confirm --> Verify
```

Конфликт считается разрешённым не потому, что инструмент выбрал правдоподобный текст, а потому,
что применённая стратегия сохранила обязательные инварианты и прошла проверку. Подробная политика
зафиксирована в ADR 0002.
