# Интеграция CodeSplit с ИИ через MCP

## Назначение

MCP-сервер позволяет локальному агентскому ИИ использовать CodeSplit как набор проверяемых
инструментов. Модель помогает сформулировать архитектурное намерение, но не получает право напрямую
переписывать исходники от имени CodeSplit.

Целевая схема:

```text
Пользователь → локальный ИИ → Python MCP Server → CodeSplit Core → Clang/CMake
                                      ↘ CLI JSON на первом этапе
```

CLI и MCP являются адаптерами одного ядра. Правила допустимости, построение replacements,
транзакция, rollback и проверка результата не реализуются повторно в Python.

## Почему Python

Python выбран для MCP-адаптера, потому что позволяет быстро реализовать протокольный слой, имеет
зрелые средства работы с JSON, subprocess и тестированием, а также хорошо подходит для интеграции с
локальными агентами. Производительность семантического анализа от этого выбора не зависит: тяжёлая
работа остаётся в C++-ядре и Clang.

Это решение не означает перенос CodeSplit на Python. Граница процесса дополнительно изолирует
протокол и зависимости MCP от C++-ядра.

## Разделение ответственности

### ИИ

- понимает запрос на естественном языке;
- выбирает из доказанно доступных кандидатов;
- предлагает смысловые группы;
- предлагает каталоги и понятные имена файлов;
- объясняет план пользователю и принимает корректировки;
- вызывает только опубликованные MCP-инструменты.

### CodeSplit

- загружает настоящую compilation database;
- строит AST и граф доказанных зависимостей;
- сообщает блокеры и границы поддержки;
- проверяет группы, имена и пути;
- рассчитывает фактическое уменьшение с учётом wrapper;
- формирует точный preview;
- применяет изменения транзакционно;
- обновляет build graph, повторно анализирует и собирает проект;
- выполняет rollback и сообщает его результат.

### Пользователь

- подтверждает смысловое разбиение либо корректирует его;
- видит точный набор файловых изменений;
- отдельно разрешает изменяющую операцию.

## Сценарий уменьшения файла

Запрос:

```text
Раздели методы в a.cpp по смысловым группам и уменьши файл до 85 KiB.
```

Последовательность:

1. ИИ вызывает `analyze_file` и `list_candidates`.
2. CodeSplit возвращает размер файла, сущности, USR, диапазоны, зависимости, ограничения и
   предполагаемое уменьшение при переносе.
3. ИИ предлагает, например, группы `newton`, `validation` и `serialization`, каталог каждой группы
   и имена `newton_a.cpp`, `validation_a.cpp`, `serialization_a.cpp`.
4. Пользователь подтверждает структуру или меняет состав, размещение и имена.
5. ИИ вызывает `plan_file_reduction`. План содержит точный лимит в байтах, выбранные USR, целевые
   пути, порядок шагов, ожидаемые размеры и хеши входных файлов.
6. CodeSplit проверяет план и возвращает preview без записи.
7. После явного подтверждения `apply_plan` выполняет группы последовательно. После каждого шага
   повторяются анализ, сборка и измерение файла.
8. CodeSplit останавливается при достижении лимита или когда безопасных кандидатов больше нет.

Частичный результат является штатным и объяснимым состоянием, а не ложным успехом:

```json
{
  "status": "partial",
  "target_size_bytes": 87040,
  "actual_size_bytes": 98304,
  "target_reached": false,
  "remaining_excess_bytes": 11264,
  "applied_groups": ["newton", "validation"],
  "remaining_blockers": ["unsupported_dependency"]
}
```

## Группировка, размещение и нейминг

Группа содержит стабильные идентификаторы сущностей, а не только отображаемые имена. Источниками
группы могут быть:

- явный выбор пользователя;
- класс или namespace;
- граф прямых зависимостей и strongly connected component;
- набор, необходимый для достижения лимита;
- смысловое предложение ИИ.

Параметры размещения:

- `output_directory` — относительный каталог внутри разрешённого корня проекта;
- `target_file` — точное имя файла с наивысшим приоритетом;
- `group` — логическое имя для отчёта и детерминированного шаблона;
- шаблон по умолчанию — `{group}_{source_stem}.cpp`.

ИИ может предложить `newton_a.cpp`, но CodeSplit нормализует и проверяет результат. Запрещены выход
за пределы проекта, абсолютный неподтверждённый путь, регистровая коллизия, зарезервированное имя,
неявное перезаписывание и добавление файла в недоказанную build target.

Если файл существует, CodeSplit возвращает явные варианты: дополнить совместимый файл, выбрать
другое имя или отменить операцию. Автоматическое создание `name_2.cpp` без отображения решения не
допускается.

## Контракт инструментов

Первый read-only набор:

- `doctor` — проверка окружения и готовности проекта;
- `analyze_file` — полный структурированный анализ;
- `list_candidates` — кандидаты с прогнозом уменьшения и блокерами;
- `explain_candidate` — объяснение зависимостей конкретной сущности;
- `plan_extraction` — план одной сущности или заданной группы;
- `preview_extraction` — точные изменения без записи;
- `plan_file_reduction` — упорядоченный план до заданного размера;
- `get_status` — состояние продолжительной или прерванной операции.

Изменяющий набор:

- `apply_plan`;
- `continue_reduction`;
- `rollback`.

Каждый план получает `plan_id`, версию схемы и хеши всех входов. `apply_plan` требует `plan_id`, те же
хеши и явный признак подтверждения. Изменение исходника, build file или конфигурации после preview
делает план устаревшим и требует повторного анализа.

## Подтверждения

По умолчанию используются два рубежа:

1. подтверждение смысловой структуры — состава групп, каталогов и имён;
2. подтверждение точного preview — replacements и изменений build graph.

Клиент может предложить объединённый режим только как явно выраженное намерение пользователя.
Ошибки, блокеры, rollback и частичный результат показываются всегда.

## Транспорт и безопасность

Первый транспорт — локальный `stdio`. Stdout содержит только сообщения протокола; логи CodeSplit,
вывод дочерних процессов и прогресс направляются в stderr либо возвращаются структурированными
полями. Это предотвращает повреждение JSON-RPC выводом CMake или компилятора.

Сервер обязан:

- работать только внутри настроенных разрешённых корней;
- проверять canonical path и symlink перед чтением и записью;
- не принимать путь только на основании текстового префикса;
- не применять план с несовпавшими хешами;
- не выполнять изменяющий инструмент без подтверждения;
- сохранять подробный журнал шагов и проверок;
- использовать транзакцию и rollback ядра, а не собственные файловые операции Python.

## Этапы реализации

1. Зафиксировать JSON-схемы CLI, подробные ошибки и стабильные exit codes.
2. Реализовать Python stdio-сервер для read-only инструментов через subprocess и `--format json`.
3. Добавить контракт групп, размещения, нейминга и планирования до размера.
4. Добавить plan store с идентификаторами, хешами и сроком жизни.
5. Подключить preview и только затем изменяющие инструменты.
6. Провести end-to-end проверку с локальным агентом компании.
7. После стабилизации выделить прямой CodeSplit Core API, сохранив CLI как самостоятельный интерфейс.

Перед интеграцией с корпоративным агентом необходимо уточнить поддерживаемую версию MCP, транспорт
`stdio`, способ показа подтверждений, поддержку прогресса и ограничения рабочих каталогов.
