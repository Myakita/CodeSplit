# ADR 0009: сохранять связывание callable и anonymous namespace отдельно

- Статус: принято
- Дата: 2026-08-13

## Контекст

Перенос определения между файлами может изменить видимость символа, нарушить ODR или создать
конфликт имён. Обычная namespace-функция, функция с `static` и функция в anonymous namespace
имеют разные требования к допустимой области переноса, даже если некоторые из них одинаково
недоступны другим единицам трансляции.

Clang различает `None`, `Internal`, `UniqueExternal`, `VisibleNone`, `Module` и `External`.
Дополнительно в C++20 функция anonymous namespace возвращает `Internal`, поэтому linkage сам по
себе не объясняет происхождение ограничения.

## Решение

`CallableDefinition` содержит `SymbolLinkage` со значениями `none`, `internal`,
`unique_external`, `module` и `external`. Значение берётся из семантической декларации Clang, а не
определяется по написанию `static`.

Отдельное поле `in_anonymous_namespace` вычисляется обходом родительских `DeclContext`. Оно
сохраняет факт нахождения функции или метода внутри unnamed namespace независимо от категории
linkage, выбранной конкретным стандартом языка и версией frontend.

Text и JSON отчёты выводят оба значения. `VisibleNone` сворачивается в публичное `none`, а
`Invalid` безопасно обрабатывается тем же значением.

## Рассмотренные альтернативы

### Проверять только ключевое слово `static`

Отклонено: internal linkage возникает не только из-за `static`, а текстовый поиск не учитывает
семантику декларации и контекст класса или пространства имён.

### Хранить только `isExternallyVisible`

Отклонено: булево значение смешало бы `static`, anonymous namespace, отсутствие linkage и
потенциальную module visibility, хотя для них нужны разные стратегии переноса.

### Использовать только formal linkage

Отклонено: формальная категория может скрыть уникальность anonymous namespace, важную для
безопасности декомпозиции.

### Считать любое internal linkage признаком anonymous namespace

Отклонено: обычная `static` функция также имеет internal linkage. Красный тест показал, что в
C++20 обе конструкции получают одинаковую категорию Clang.

## Последствия

Положительные:

- план переноса сможет отличать публичный символ от сущности, ограниченной единицей трансляции;
- `static` и anonymous namespace не смешиваются;
- модель готова к module linkage и особенностям других языковых режимов;
- результат основан на семантике Clang, а не на тексте объявления.

Ограничения:

- linkage типов и глобальных переменных пока не экспортируется;
- видимость атрибутов DLL и ELF не представлена отдельным полем;
- публичный `none` объединяет `None` и редкий Clang-случай `VisibleNone`;
- автоматическая стратегия переноса для internal callable ещё не реализована.
